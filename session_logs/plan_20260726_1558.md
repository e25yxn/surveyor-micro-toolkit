## 2. ข้อสรุปเชิงสูตรที่ต้องบันทึก (ปรับถ้อยคำจากแผนแม่ 1 จุด)

แผนแม่ข้อ 2.3 (4) เขียนว่า *"มุม deflection ตามแบบจริง = มุมระหว่างเวกเตอร์ (PI→PC จริง)
กับ (PI→PT จริง)"* — **ถ้าทำตามตัวอักษรจะได้ `180° − Δ` ไม่ใช่ `Δ`** เพราะเวกเตอร์
PI→PC ชี้ย้อนกลับทางเดินทาง แล้วสูตรข้อ (5) `T/tan(Δ/2)` ต้องการ `Δ` ตัวจริง

**สิ่งที่ implement จริง** (ให้ขนานกับสูตรฝั่งออกแบบเป๊ะๆ ใช้ helper ชุดเดียวกัน):

```
az_in_drawn  = azimuth(PC → PI)      # ทิศเดินทางขาเข้า
az_out_drawn = azimuth(PI → PT)      # ทิศเดินทางขาออก
Δ_drawn      = angleDiff(az_out_drawn, az_in_drawn)     # เครื่องหมาย + = เลี้ยวขวา
```

เทียบกับฝั่งออกแบบที่ใช้สูตรเดียวกันแต่เปลี่ยนจุด:

```
az_in_design  = azimuth(PI[v-1] → PI[v])
az_out_design = azimuth(PI[v] → PI[v+1])
Δ_design      = angleDiff(az_out_design, az_in_design)
```

`Δ_design` **คำนวณซ้ำเอง ไม่แตะ `GS_AlignmentBuilder.gs`** (ตรงตามแผนแม่ข้อ 2.3(7))
ยืนยันแล้วว่าสูตรตรงกับ `buildFromPI` บรรทัด 136-138 ทุกตัวอักษร

รัศมีย้อนกลับ: `R = T / tan(|Δ_drawn| / 2)` ใส่เครื่องหมายตาม `sign(Δ_drawn)`

### 3.2 ΔRadius ควรเทียบแบบมีเครื่องหมายหรือไม่?

`buildFromPI` **ไม่สนใจเครื่องหมายของ R ในตารางเลย** (บรรทัด 139 `sgn = delta >= 0 ? 1 : -1`
แล้วบรรทัด 77 `Math.abs(vert.R)`) — เครื่องหมาย R ในตารางจึงเป็นแค่เอกสารประกอบ

* ถ้าใช้ `ΔR = R_calc − R_design` แบบมีเครื่องหมาย: R ที่ใส่เครื่องหมายผิดจะโชว์ ΔR ≈ 1000 ม.
  ซึ่ง**เกินจริงและทำให้เข้าใจผิด** (แนวที่สร้างออกมาไม่ได้ผิดเลย)
* ถ้าใช้ `ΔR = |R_calc| − |R_design|`: จับความคลาดของขนาดได้ตรง แต่**มองไม่เห็นเครื่องหมายผิด**

**ข้อเสนอ**: ใช้ `ΔR = |R_calc| − |R_design|` **บวกคอลัมน์ `SignOK`** (TRUE/FALSE) ที่เทียบ
`sign(R_design)` กับ `sign(Δ_drawn)` แยกต่างหาก — ได้ทั้งตัวเลขที่ไม่หลอกและยังจับเครื่องหมายผิดได้
(ข้อมูลชุดนี้ `SignOK` เป็น TRUE ครบทุกแถว)

## 5. โครงสร้าง `GS_CrossCheck.gs`

```
GS_CrossCheck = {
  // --- ตาราง 2a (mirror check.py::check_horizontal) ---
  POINTS_HEADER      : ['Name','STA','dN','dE','Gap','OK']
  snapToAlignmentEnds_(sta, elements, snap=0.01)   // port _snap_to_alignment_ends
  checkPoints(elements, drawing, tol=0.05)         // -> [{name,sta,deltaN,deltaE,gap,ok}]
  pointsToRows(results)                            // -> array of row arrays

  // --- ตัวช่วยจับคู่ PI <-> PC/PT จากตารางดิบ (แผนแม่ 2.4 ทางเลือก (ก)) ---
  scanRawRows_(rows)        // เดิน rows ดิบ ติด kind='vertex'|'drawing'|'sub' + vertexIndex
  neighbourPoint_(recs, i, step, wantName)         // เพื่อนบ้านที่ไม่ใช่ sub-row ตัวแรก

  // --- ตาราง 2b/2c (logic ใหม่) ---
  RADIUS_HEADER      : ['Name','R design','T_in','T_out','R from T_in',
                        'R from T_out','dR (T_in)','dR (T_out)','SignOK','Note']
  DEFLECTION_HEADER  : ['Name','Deflection design (deg)','Deflection drawn (deg)',
                        'dDeflection (deg)','dDeflection (sec)']
  checkPiCurves(rows, vertices)                    // -> [{...}] หนึ่งเรคคอร์ดต่อ PI โค้งธรรมดา
  radiusToRows(checks)
  deflectionToRows(checks)
}
```

**การจับคู่ PI ↔ PC/PT** (แผนแม่ข้อ 2.4 — เลือกทางเลือก (ก)):
`scanRawRows_()` เดินตาม `rows` **ดิบก่อน split** จึงคงลำดับสลับเดิมไว้ครบ และนับ
`vertexIndex` ไปพร้อมกัน (compound sub-row ที่ POINT ว่าง **ไม่กิน index** ตรงกับพฤติกรรม
`parsePiTable`) → ใช้ `vertexIndex` ชี้กลับเข้า `vertices[]` ได้ตรงตัว ไม่ต้องแก้
`GS_TableSplitter.gs`

**กติกาเพื่อนบ้าน**: แถวที่ติดกับ PI (ข้ามแถว compound sub-row) ต้องเป็นแถว drawing ชื่อ
`PC` (ฝั่งก่อน) / `PT` (ฝั่งหลัง) เท่านั้น — ถ้าเป็น vertex row ชื่อ BP/PI-n หรือชื่ออื่น
ถือว่าไม่มี **ยกเว้นกรณีเดียว**: ถ้าเพื่อนบ้านเป็น vertex row ชื่อ `EP` ให้ตรวจสอบก่อนว่า
PT ที่ engine คำนวณได้จริงสำหรับ PI นั้นอยู่ใกล้ EP ภายใน snap tolerance (0.01 ม. ตาม
`_snap_to_alignment_ends`) หรือไม่ — ถ้าใกล้พอ ให้ใช้พิกัด EP แทน PT ที่ขาดหาย (กรณี PI-11)
ถ้าไม่ใกล้พอ ให้ถือว่าไม่มี PT เหมือนเดิม (fallback ไปใช้ Δ_design ตามข้อ 3.1)
ตรวจแล้วว่ากติกานี้ให้ผลถูกต้องครบทั้ง 11 PI ในไฟล์จริง

**เงื่อนไข skip ของ 2b/2c**: `vertex.compound` มี / `Ls`,`LsIn`,`LsOut` ตัวใดตัวหนึ่งไม่ว่าง /
ไม่มี `R` — ในไฟล์จริง skip แค่ **PI-10** (CLOTHOID Ls=67.5)
