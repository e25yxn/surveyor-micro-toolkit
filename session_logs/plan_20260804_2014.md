## 1. การตัดสินใจที่ยืนยันแล้ว (ปิดคำถามเปิดทั้ง 3 ข้อ)

| คำถามเปิด | ตัดสินใจ | เหตุผลสรุป |
|---|---|---|
| Threshold | **A** — raw `tan_len_signed < 0` ไม่มี tolerance | ตรงรายงานเป๊ะ ไม่เดาค่าคงที่ใหม่ที่ไม่มีหลักฐาน หลีกเลี่ยงปัญหาเดียวกับ finding #17 |
| แยก 2 เงื่อนไข (ซ้อนทับจริง vs tangent สั้น) | **A** — เช็คเดียว | dot<0 คือ correctness bug แท้ ส่วน dot>0 เล็กๆ เป็นความเห็นด้าน design-standard ที่ core ไม่ควรมีความเห็น (ต่างจาก Fix #1 ที่ 2 เงื่อนไขเป็น danger radius ของสมการเดียวกัน) |
| Fallback | **B** — append issue, ไม่ raise, ไม่ fallback angle-point, geometry เดิม | ไม่มี fallback ที่ "แก้ปัญหาจริง" ได้แบบ Fix #1 (ปัญหาคือความสัมพันธ์ระหว่างโค้ง 2 ตัว ไม่ใช่รูปทรงของโค้งเดียว) — B ให้ผู้ใช้เห็น warning ชัดเจนโดยไม่ทำให้ไฟล์ทั้งไฟล์ build ไม่ได้ |

### โค้ดที่เสนอ (เพิ่ม, ไม่ลบของเดิม — geometry output เหมือนเดิมทุกประการ
ตามที่ fallback=B กำหนด)
```python
tan_len = wcb.calculate_distance_2d(prev_n, prev_e, curve_start_n, curve_start_e)
sta_cs  = prev_sta + tan_len

# FIX (Oracle correction, session_logs/review_src_smt_20260802.md #2,
# session_logs/plan_20260804_2014.md): tan_len ข้างบนเป็นระยะทางไม่มี
# เครื่องหมาย (hypot) ทำให้โค้งที่ tangent ไม่พอ (ซ้อนทับกัน) ไม่ถูกตรวจจับเลย
# — prev และ curve_start อยู่บนเส้นตรงเดียวกันโดยโครงสร้างเสมอ (ทิศทาง
# azimuth_in) จึง dot product ตรงนี้คือระยะโปรเจกชันที่มีเครื่องหมายจริง ไม่ใช่
# การประมาณ ค่าติดลบ = curve_start อยู่หลัง prev = โค้งซ้อนทับกันจริง
# ไม่มี fallback ที่แก้ปัญหาได้แบบ Fix #1 (ปัญหาอยู่ที่ความสัมพันธ์ระหว่างโค้ง
# สองตัว ไม่ใช่รูปทรงของโค้งเดียว) — เลือก append issue เท่านั้น geometry
# ยังคงเดิมทุกประการ (ผู้ใช้ต้องแก้ R/Ls หรือระยะห่าง PI ในไฟล์ input เอง)
# หมายเหตุ: prev อาจเป็น BP เอง (v==1) ไม่ใช่แค่ PI ก่อนหน้า — เคสนี้เกิดขึ้น
# จริงได้เมื่อ PI แรกมี R ใหญ่พอที่ curve_start ย้อนไปก่อน BP (พิสูจน์แล้วใน
# session_logs/tmp_verify_bug2_curve_overlap.py: PI#1 ในสคริปต์นั้นเอง
# ก็ tan_len_signed=-77.124 ติดลบเช่นกัน แยกจากปัญหา PI#2 vs PI#1)
dn = curve_start_n - prev_n
de = curve_start_e - prev_e
tan_len_signed = dn * math.cos(azimuth_in) + de * math.sin(azimuth_in)
if tan_len_signed < 0:
    prev_label = 'BP' if v == 1 else f'PI#{v - 1}'
    issues.append(
        f'PI#{v}: จุดเริ่มโค้ง (curve_start) อยู่หลังจุดจบของ {prev_label} '
        f'ตามทิศทาง azimuth_in ({fpmath.rad_to_deg(azimuth_in):.4f}°) — '
        f'โค้งซ้อนทับกัน (tan_len_signed = {tan_len_signed:.4f} m, ต้อง >= 0) '
        f'ตรวจสอบ R/Ls หรือระยะห่างระหว่าง {prev_label} และ PI#{v}'
    )

elements.append(make_element(
    'T', prev_sta, sta_cs, prev_n, prev_e, fpmath.rad_to_deg(azimuth_in), 0,
))
control.append(ControlPoint(
    name=name_scheme['start'], sta=sta_cs, n=curve_start_n, e=curve_start_e,
))
```

**ชื่อตัวแปร:** ใช้ `tan_len_signed` (ไม่ใช่ `dot_product`) — มีความหมาย
เชิงเรขาคณิตชัดกว่า ตั้งชื่อคู่กับ `tan_len` (unsigned) ที่มีอยู่แล้วบรรทัดบนสุด
สื่อว่าเป็นค่าเดียวกันแค่คนละ sign convention — ตรงกับ naming convention
ของโปรเจกต์ (CLAUDE.md: "ubiquitous language")

**ทำไม `abs(tan_len) == abs(tan_len_signed)` เสมอ (สมมติฐาน collinearity):**
`prev` และ `curve_start` อยู่บนเส้น `azimuth_in` เดียวกันโดยโครงสร้าง
ยืนยันเชิงประจักษ์แล้วจากสคริปต์ reproduce ทั้งสองเคส (PI#1 vs BP:
`tan_len_signed=-77.124` ตรงกับ `-tan_len` เป๊ะ; PI#2 vs PI#1:
`tan_len_signed=-330.7850` ตรงกับ `-tan_len` เป๊ะ) — component ตั้งฉาก
เป็น 0 ทั้งคู่ ไม่มี residual — ไม่ต้องเพิ่ม guard สำหรับ non-collinear case
