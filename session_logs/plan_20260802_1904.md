## 2. วิธีแก้ที่เสนอ + เหตุผลทางวิศวกรรม

### สูตรเดิม (บรรทัด 387-392 เดิม)
```python
# Solve 2×2 system: d1·uIn + d2·uOut = V
v_n, v_e = _calculate_end_displacement(subs, azimuth_in, sign)
det = math.sin(delta)                              # = sin(az_out − az_in)
d1  = (v_n * math.sin(azimuth_out) - v_e * math.cos(azimuth_out)) / det
```
`delta` มาจาก `fpmath.calculate_angle_diff` ซึ่งคืนค่าในช่วง `(-π, π]` เสมอ ดังนั้น
`sin(delta) = 0` เกิดได้ที่ **2 จุดเท่านั้น**: `delta ≈ 0` (สามจุดเรียงเส้นตรง) กับ
`delta ≈ ±π` (หักกลับ 180°) — พิสูจน์ทั้งสองกรณีแยกกันด้วยคณิตศาสตร์จริง (ไม่ใช่
เดา) ตาม Extension policy ข้อ 3:

**กรณี delta≈0 (collinear):** เขียน v_n, v_e ของกลุ่มโค้งวงกลมล้วนในเทอมของ delta
ได้ `v_n = R sin(δ)`, `v_e = R(1−cos δ)` (สูตร chord มาตรฐาน) แทนใน d1:
```
d1 = R·sin(az_out) − R·[(1−cos δ)/sin δ]·cos(az_out)
```
เมื่อ `δ→0`, `(1−cos δ)/sin δ → δ/2 → 0` (limit ไม่มี singularity จริง — เป็น
removable singularity ทางคณิตศาสตร์) ดังนั้น `d1 → R·sin(az_out)` ซึ่งเป็นค่าจำกัด
เสมอ **แต่ Python หาร 0.0/0.0 ตรงๆ ไม่ทำ limit ให้ — ได้ ZeroDivisionError ทันที
ที่ δ เท่ากับ 0.0 พอดี (float exact)** ยืนยันจริงด้วย Case A (ดูข้อ 3) นอกจากนี้
ที่ δ≈0 พอดี ความยาวโค้งที่ขอ (`R·|δ|`) ก็ ≈ 0 อยู่แล้ว — ไม่มีโค้งจริงให้สร้าง
ทางกายภาพ จึงสมเหตุสมผลที่จะไม่พยายามแก้สมการ แต่ข้ามไปใช้เส้นทาง angle-point
(tangent-tangent) ที่มีอยู่แล้วจาก EXT-001 แทน — EXT-001 เองก็ระบุเงื่อนไข
"สามจุดเรียงเส้นตรง (deflection=0)" ไว้ในตารางแล้ว (docs/extensions.md บรรทัด 28)
เพียงแต่โค้ดปัจจุบันไม่ได้ implement เงื่อนไขนี้จริงเมื่อผู้ใช้ระบุ R มาด้วย
(ทำงานเฉพาะตอน R ว่าง/0) — แผนนี้ทำให้โค้ดตรงกับที่ EXT-001 เอกสารสัญญาไว้จริงๆ

**กรณี delta≈π (หักกลับ 180°):** นี่คือ singularity แท้ ไม่ใช่ removable —
`d1 ≈ R·sin(az_out) − 2R·cos(az_out)/x` เมื่อ `x = π−δ → 0` (พิสูจน์ด้วย Taylor
expansion รอบ π) พจน์ `1/x` พุ่งไม่จำกัดจริง **นี่คือ singularity เดียวกับสูตร
มาตรฐานของ tangent length โค้งวงกลม `T = R·tan(Δ/2)`** ซึ่ง `tan(π/2)` ไม่นิยาม —
อ้างอิงเดียวกับที่ EXT-001 ใช้ (*AASHTO A Policy on Geometric Design of Highways
and Streets*, Green Book) โค้งที่มุมเบี่ยง 180° ไม่มีอยู่จริงในงานวิศวกรรมถนน
(hairpin โค้งแคบสุดในภูเขาก็ยังต่ำกว่า 180° มาก) — ไม่มีทางแก้สมการนี้ให้ได้ค่าที่
สมเหตุสมผล จึงต้องดักไว้เช่นกัน ยืนยันเชิงประจักษ์ด้วย Case C (station พุ่งไป ~2
พันล้านเมตรแบบไม่มี error/issue เลย — ดูข้อ 3)

### Guard ที่เสนอ (แทรกก่อนบรรทัด `if not subs:` เดิม)
```python
subs, issue = _build_curve_sub_elements(vertices[v], abs_delta)
if issue:
    issues.append(f'PI#{v}: {issue}')

# EXTENSION: beyond oracle (Oracle correction exception, 2026-08-02, review #1) —
# sin(delta)≈0 ทำให้สมการ 2x2 ด้านล่าง singular ใน 2 กรณี: delta≈0 (collinear —
# removable singularity ทางคณิตศาสตร์ แต่ Python หาร 0.0/0.0 ตรงๆ ไม่ limit ให้ และ
# ความยาวโค้งที่ขอก็ ≈0 อยู่แล้วไม่มีโค้งจริงให้สร้าง) และ delta≈π (หักกลับ 180° —
# singularity แท้ ไม่ removable เหมือนสูตร tangent length มาตรฐาน T=R·tan(Δ/2) ที่
# ไม่นิยามที่ Δ=π; AASHTO Green Book, ดู EXT-001) ทั้งสองกรณีข้ามไปใช้เส้นทาง
# angle-point (tangent-tangent) ด้านล่างแทนการหารต่อ — ดู
# session_logs/plan_20260802_1904.md, docs/extensions.md.
if subs and abs(math.sin(delta)) < fpmath.EPS:
    issues.append(
        f'PI#{v}: มุมเบี่ยง {fpmath.rad_to_deg(delta):.6f}° ทำให้หาจุดเริ่มโค้งไม่ได้ '
        '(sin(Δ)≈0 — เรียงเส้นตรงหรือหักกลับ 180°) ใช้ angle point (IP) แทนโค้งที่ระบุ'
    )
    subs = []

# EXTENSION: beyond oracle — no-curve PI (angle point or collinear).
# Emits a tangent element to the PI vertex, records it as 'IP', and continues.
if not subs:
    tan_len = wcb.calculate_distance_2d(prev_n, prev_e, vertex_n, vertex_e)
    ...   # (โค้ดเดิมจากบรรทัดนี้ลงไปไม่เปลี่ยน)
```

**หมายเหตุ comment เดิม:** บรรทัด 376 เดิม ("This also avoids ZeroDivisionError
when det = sin(delta) = 0 (collinear case)") **เป็นข้อความที่คลาดเคลื่อน** —
จริงๆ แล้ว guard เดิม (`if not subs`) ป้องกัน ZeroDivisionError ได้เฉพาะตอน R
ว่าง/0 เท่านั้น (subs ว่างตั้งแต่ `_build_curve_sub_elements` คืนมา) ถ้า R ถูกระบุ
มาด้วยและ delta≈0/π พอดี โค้ดเดิมไหลผ่าน `if not subs:` (เพราะ subs ไม่ว่าง)
ไปหารที่บรรทัด 392 จริง — แผนนี้จะตัด claim ที่ผิดออกจาก comment เดิม (ลบประโยค
"This also avoids ZeroDivisionError...") เพื่อไม่ให้เข้าใจผิดซ้ำอีก

**ทำไมเลือก fallback เป็น angle-point แทน raise ValueError:** เพราะทั้งสองกรณี
(delta≈0, delta≈π) มี fallback ที่ปลอดภัยและมี precedent อยู่แล้วจาก EXT-001
(ต่างจากบั๊ก #3 ที่ compound/RADIUS กำกวมจริงๆ จนต้อง raise เพราะระบบเดาไม่ได้)
— การ raise ตรงนี้จะทำให้ไฟล์ PI ทั้งไฟล์ build ไม่ได้เลยแค่เพราะ PI ตัวเดียวเสีย
ทั้งที่มี fallback ที่สมเหตุสมผลอยู่แล้ว และ issue message ที่เพิ่มเข้าไปทำให้ผู้ใช้
เห็นปัญหาชัดเจนไม่เงียบเหมือนเดิม (ต่างจากบั๊กเดิมที่ Case C ไม่มี issue เลย)

## Addendum (2026-08-02, หลัง implement รอบแรก) — single threshold ไม่พอ ต้องแยกเป็น 2 เงื่อนไข

คำถามเปิดข้อ 3 ด้านบน (threshold `fpmath.EPS`=1e-9 เหมาะสมหรือไม่) ได้คำตอบจาก
การ implement จริง: **ไม่เหมาะสม** สำหรับฝั่ง delta≈π — แผนเดิมเสนอ guard เดียว
`abs(math.sin(delta)) < fpmath.EPS` ครอบทั้ง 2 กรณี แต่พอเขียน regression test
จริงด้วย geometry ของเคส C ที่ยืนยันปัญหาไว้ตั้งแต่ต้น (BP(0,0)→PI(500,0,R=200)→
EP(0,0.0001), delta≈180°) test ล้มเหลว — ตรวจด้วย diagnostic script
(`session_logs/tmp_diag_case1_test_failure.py`) พบว่า `sin(delta)` ของเคสนี้จริงๆ
คือ **1.9999999890696914×10⁻⁷** ซึ่งใหญ่กว่า `fpmath.EPS`=1×10⁻⁹ ถึง ~200 เท่า —
guard เดิมจึงไม่ trigger เลย และ station ยังพุ่งไปหลักพันล้านเมตรแบบเงียบเหมือนก่อนแก้

### สาเหตุ: `abs(sin(delta))` ค่าเดียวแยกไม่ออกว่า "ใกล้ 0" หรือ "ใกล้ π"
สอง singularity เป็นคนละประเภทตามที่พิสูจน์ไว้ในข้อ 2 ของแผนหลักแล้ว:
- **delta≈0**: removable singularity — d1 ยัง well-conditioned ลงไปจนถึง float
  จริงศูนย์ threshold แคบ (1e-9) เพียงพอและถูกต้องอยู่แล้ว (พิสูจน์จาก test เคส A
  และเคส B ที่ยังผ่านทั้งคู่)
- **delta≈π**: non-removable singularity — `d1 ~ 2R/(π−|delta|)` พุ่งแบบ 1/x
  ตรงๆ "รัศมีอันตราย" ในเทอมของระยะห่างจาก π กว้างกว่ามาก ต้องใช้ threshold ที่ใหญ่กว่ามาก

`abs(sin(delta))` เป็นค่าเดียวที่ผสมทั้งสองแกน (มุมใกล้ 0 กับมุมใกล้ π ต่างก็ทำให้
sin เข้าใกล้ 0 เหมือนกัน) จึงไม่สามารถตั้ง threshold เดียวที่แคบพอสำหรับฝั่ง 0
(ไม่กิน legit curve) และกว้างพอสำหรับฝั่ง π (จับ blowup จริง) พร้อมกันได้ในตัวเดียว
— ต้องแยกเป็น 2 เงื่อนไขอิสระด้วย `or`

### วิธีแก้ที่ใช้จริง
```python
if subs and (
    abs(math.sin(delta)) < fpmath.EPS                      # เดิม: delta≈0
    or abs(math.pi - abs(delta)) < _NEAR_PI_EPS             # ใหม่: delta≈π
):
```
เงื่อนไข delta≈0 เดิมไม่ถูกแตะเลย เพิ่มเงื่อนไข delta≈π แยกอิสระด้วย `abs(math.pi
- abs(delta))` (วัดระยะห่างจาก π โดยตรง แทนที่จะวัดผ่าน sin ที่กำกวม)

### ที่มาของ `_NEAR_PI_EPS = 1e-4`
ไม่ใช่ค่าที่เดาขึ้นมา — มาจากการคุยกับ CK1024 เรื่อง noise floor จริงในงานสำรวจ:
พิกัด input จากแบบ (Civil 3D) ที่ปัดทศนิยม 3 ตำแหน่งตามธรรมเนียมงานสำรวจ ทำให้เกิด
rounding noise สะสมทั่วทั้งระบบ — CK1024 ยืนยันด้วยไฟล์ Civil 3D จริงของตัวเอง:
เมื่อขยายทศนิยมพิกัดเป็น 15 ตำแหน่งแล้วเช็คคู่จุด BP-PC ที่ควรเป็นจุดเดียวกันทาง
ทฤษฎี พบว่าห่างกันจริง ~1×10⁻⁷ เมตรทุกครั้งที่เช็ค (ไม่ใช่ครั้งเดียว) — นี่คือ noise
floor จริงของระบบ ไม่ใช่ค่าสมมติ

`_NEAR_PI_EPS = 1×10⁻⁴` (~20 arcsec จาก π พอดี) อยู่เหนือ noise floor นี้ ~1,000 เท่า
(กันไม่ให้ noise ธรรมดาทำให้ curve จริงถูกเบี่ยงไป angle-point โดยไม่ได้ตั้งใจ) และ
ยังห่างจากมุมเบี่ยงของ hairpin โค้งจริงที่แคบที่สุดในงานวิศวกรรมถนน (~170-175°,
เทียบเท่า ~0.087-0.17 rad จาก π) มาก — จึงไม่มีทางกิน design โค้งจริงใดๆ เข้าไปในเส้นทาง
angle-point โดยไม่ตั้งใจ ขณะที่ยังกว้างพอจับเคส C (x≈2×10⁻⁷) ได้สบายๆ (ห่างจาก
threshold ~500 เท่า)
