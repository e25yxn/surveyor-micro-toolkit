# Plan — F.6.2 แก้บั๊ก TypeError "reading 'n'" ตอนเลือก sheet/tab ว่างเปล่า

อ้างอิง root cause จาก F.6.1 (session_logs/latest.md entry `[2026-08-02 08:00]`)
และการอนุมัติแนวทางแก้จาก Claude (แชท) — ปรับเงื่อนไข guard เป็น `N < 2` (ไม่ใช่
`N === 0`) ตามที่ CK1024 สั่งแก้

## สรุปปัญหา (ทวนสั้นๆ)

`GS_AlignmentBuilder.buildFromPI(vertices)` เข้าถึง `vertices[0].n` ทันทีโดยไม่
เช็คว่ามีข้อมูลพอหรือไม่ เมื่อ sheet/tab ที่เลือกว่างเปล่า (ไม่มีแถวข้อมูลเลย หรือ
มีแค่ header) `GS_PiTableParser.parsePiTable` จะคืน `vertices = []` อย่างถูกต้อง
(ไม่ throw) แต่ `buildFromPI` ไม่มี guard จึงพัง TypeError ดิบๆ หลุดออกไปที่ผู้ใช้
โดยไม่มีความหมาย

**เหตุผลที่ guard ต้องเป็น `N < 2` ไม่ใช่ `N === 0`:** alignment ต้องมีอย่างน้อย
BP + EP สองจุดขึ้นไปถึงจะมีความหมาย (มี tangent อย่างน้อย 1 เส้น) ถ้ามีแค่ 1 จุด
(เช่น sheet มีแค่แถว BP แถวเดียว ไม่มี EP) โค้ดปัจจุบันจะไม่ throw แต่จะคำนวณโดย
ใช้ `vertices[0]` ซ้ำเป็นทั้ง BP และ EP (บรรทัด `var ep = vertices[N - 1]` จะได้
`vertices[0]` เดิมตอน N=1) ได้ elements ที่มี station เริ่ม=จบ ระยะทาง 0 —
ไม่ error แต่ output ไม่มีความหมายทางวิศวกรรม (silent garbage แย่กว่า throw ชัดๆ)

## ไฟล์ที่จะแก้ (2 ไฟล์)

### 1. `reference/gsheet/GS_AlignmentBuilder.gs`

**ตำแหน่ง:** บรรทัด 128-132 (ต้นฟังก์ชัน `buildFromPI`)

**ปัจจุบัน:**
```js
function buildFromPI(vertices) {
    var els = [], control = [], issues = [];
    var N = vertices.length;
    var prev = { n: vertices[0].n, e: vertices[0].e, sta: vertices[0].sta };
    control.push({ name: 'BP', sta: prev.sta, n: prev.n, e: prev.e });
```

**แก้เป็น:**
```js
function buildFromPI(vertices) {
    var els = [], control = [], issues = [];
    var N = vertices.length;
    if (N < 2) {
      throw new Error(
        'ไม่พบข้อมูล alignment ที่ครบถ้วนในตารางนี้ — ต้องมีอย่างน้อยจุดเริ่ม ' +
        '(BP) และจุดจบ (EP) กรุณาตรวจสอบว่ากรอกข้อมูลครบหรือไม่'
      );
    }
    var prev = { n: vertices[0].n, e: vertices[0].e, sta: vertices[0].sta };
    control.push({ name: 'BP', sta: prev.sta, n: prev.n, e: prev.e });
```

หมายเหตุ: ข้อความ error เป็นภาษาไทยตรงตามที่ CK1024 กำหนด ไม่มี placeholder ต้อง
เติมทีหลัง (ต่างจาก `flushPending_()` ที่ต้องใส่ชื่อ PI/เลขบรรทัดแบบไดนามิก
เพราะเคสนี้ไม่มีบริบทอะไรให้ระบุเพิ่มได้ — sheet ว่างก็คือว่าง)

### 2. `reference/gsheet/Index.html`

**ตำแหน่ง:** `ERROR_MESSAGE_MAP` array บรรทัด 115-160 — เพิ่ม entry ใหม่ (ทางเลือก
A ที่อนุมัติแล้ว) เป็นรายการที่ 2 ต่อจาก pattern แรก (`ไม่พบ tab "..."`) เพราะเป็น
เคส "เลือกไฟล์/แท็บผิด" กลุ่มเดียวกัน ก่อนเคส `invalid numeric cell` ที่เป็นเรื่อง
ข้อมูลในตารางผิดรูป

**ปัจจุบัน (บรรทัด 116-122):**
```js
      {
        test: /^ไม่พบ tab "(.+)" ในไฟล์นี้$/,
        friendly: function (m) {
          return 'ไม่พบแท็บ (tab) ชื่อ "' + m[1] + '" ในไฟล์นี้แล้ว — ' +
            'อาจถูกลบหรือเปลี่ยนชื่อไประหว่างที่หน้านี้เปิดอยู่ กรุณาเลือกไฟล์ใหม่อีกครั้ง';
        }
      },
```

**แก้เป็น (เพิ่ม entry ใหม่ต่อท้าย ก่อน `invalid numeric cell`):**
```js
      {
        test: /^ไม่พบ tab "(.+)" ในไฟล์นี้$/,
        friendly: function (m) {
          return 'ไม่พบแท็บ (tab) ชื่อ "' + m[1] + '" ในไฟล์นี้แล้ว — ' +
            'อาจถูกลบหรือเปลี่ยนชื่อไประหว่างที่หน้านี้เปิดอยู่ กรุณาเลือกไฟล์ใหม่อีกครั้ง';
        }
      },
      {
        test: /^ไม่พบข้อมูล alignment ที่ครบถ้วนในตารางนี้/,
        friendly: function () {
          return 'ชีต/แท็บนี้ยังไม่มีข้อมูล alignment ครบถ้วน — ตรวจสอบว่าเลือก ' +
            'ไฟล์/แท็บถูกต้อง หรือกรอกข้อมูลจุดเริ่ม (BP) และจุดจบ (EP) ให้ครบก่อน ' +
            'กดคำนวณ';
        }
      },
```

`test` ใช้ `^...` จับต้นข้อความพอ (ไม่ต้อง exec ทั้งประโยคยาว) ตาม pattern เดิมที่
ไฟล์นี้ใช้อยู่แล้ว (ดู `invalid numeric cell` ก็จับแค่ต้น+ตัวแปรในวงเล็บ)

## ความเสี่ยง

- ไม่มี call site อื่นใน `reference/gsheet/*.gs` ที่เรียก `buildFromPI` ด้วย
  vertices ว่างหรือ 1 จุดโดยตั้งใจ (ตรวจแล้วด้วย grep — มีที่เดียวคือ
  `GS_Pipeline.gs:30`) จึงไม่กระทบ caller อื่น
- `smoke_test.js` ปัจจุบันไม่มีเคสทดสอบ `buildFromPI` กับ vertices ว่าง/1 จุด
  เลย (grep ยืนยันแล้ว) — การแก้นี้จึงไม่ทำให้ 23/23 เดิม fail แน่นอน แต่ก็ไม่มี
  regression coverage อัตโนมัติสำหรับเคสนี้เช่นกัน (test plan ด้านล่างจะทดสอบ
  แยกด้วย repro script ชั่วคราวแทน)
- Python `src/smt/builders/alignment_builder.py` (บรรทัด 350-352) มีช่องโหว่แบบ
  เดียวกันทุกประการ (`vertices[0]['n']` ไม่เช็คก่อน) แต่ **ไม่อยู่ในขอบเขตแผนนี้**
  เพราะ CLI ของ Python ไม่มีทางเลือก "sheet ว่างเปล่า" ผ่าน UI แบบ Google Sheets
  ได้ (ผู้ใช้ CLI ต้องป้อนไฟล์ input ที่มีข้อมูลอยู่แล้ว) — บันทึกไว้เป็น known gap
  แยกต่างหาก ถ้าจะแก้ Python ด้วยควรเป็นแผนแยกอีกฉบับ (แจ้ง CK1024 เพื่อตัดสินใจ)
- การแก้นี้เปลี่ยน error message ที่หลุดออกไปเท่านั้น ไม่กระทบ logic การคำนวณ
  ใดๆ ของเคสที่มีข้อมูลถูกต้อง (N >= 2) เลย — ความเสี่ยง regression ต่ำมาก

## Test plan

1. รัน `node reference/gsheet/smoke_test.js` — ต้องได้ 23/23 เหมือนเดิม (ยืนยัน
   ไม่กระทบของเดิม)
2. เขียน repro script ชั่วคราว (เหมือน F.6.1, ลบทิ้งหลังทดสอบผ่าน ไม่ commit)
   ป้อน 3 เคสผ่าน `GS_AlignmentBuilder.buildFromPI` โดยตรง:
   - `vertices = []` (sheet ว่างสนิท) → คาดหวัง throw ข้อความใหม่ ไม่ใช่
     TypeError
   - `vertices = [{n: 100, e: 200, sta: 0}]` (มีแค่ BP แถวเดียว ไม่มี EP) →
     คาดหวัง throw ข้อความใหม่เช่นกัน (guard `N < 2` ครอบเคสนี้ด้วย)
   - `vertices = [{n:100,e:200,sta:0}, {n:300,e:200}]` (BP+EP ปกติ ไม่มี PI) →
     คาดหวัง**ไม่** throw, ได้ `elements.length >= 1` ตามปกติ (regression check
     ว่า guard ไม่ไปบล็อกเคสปกติที่มีแค่ 2 จุด)
3. ทดสอบ `getFriendlyMessage()` แยกด้วย Node ป้อน raw message ที่ throw จริงจาก
   ข้อ 2 (เคสที่ 1 และ 2) → คาดหวังได้ friendly message ใหม่ที่เพิ่มใน
   `ERROR_MESSAGE_MAP` ไม่ใช่ catchall เดิม
4. ทดสอบจริงในเบราว์เซอร์ — เลือก sheet/tab ว่างเปล่าจริงแล้วกด "คำนวณ" ยืนยัน
   banner แสดงข้อความ friendly ใหม่ถูกต้อง + raw message ตรงกับที่ throw ใน
   `<details>`
5. `pytest -q` — คาดหวังไม่กระทบ (ไฟล์ที่แก้เป็น `.gs`/`.html` ทั้งคู่ ไม่แตะ
   Python เลย) รันเพื่อยืนยันเฉยๆ ว่าไม่มีอะไรหลุดโดยไม่ตั้งใจ
